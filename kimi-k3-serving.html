Serving a trillion parameters

Kimi K3 is Moonshot AI's open model with 2.8 trillion parameters. On 19 October 2026, Baseten's model performance team walked through how it is built and how they serve it, on a whiteboard, for an hour. This guide turns that session into plain words and diagrams: the three problems a model this size has to solve, the family tree of attention that led to its design, and the memory math that decides how many people one machine can serve.

01Why this session is worth an hourStart here

Most model launches are explained with benchmark charts. This one was explained with a memory budget. That is the more useful lens.

The session is How trillion-parameter AI models work and how to serve them (61 minutes). Philip Kiely, author of Inference Engineering, talks with Ali and Bryce from Baseten's model performance team. Ali covers the architecture and draws the history of attention on the whiteboard. Bryce covers serving: fitting the model on B300 GPUs, splitting it across chips, managing two kinds of memory, and the speed tricks on top.

The reason it matters beyond Kimi: the design choices in K3 are the ones every large model now faces. Use only a sliver of the model per word. Stop remembering every word in full. Then work out how many conversations fit in what is left of the chip's memory. If you understand this one model, you can read most model launches.

Token

A piece of text, about three quarters of a word. Models read and write tokens.

Parameter

One adjustable number inside the model. K3 has 2.8 trillion of them.

Expert

A group of parameters that only switches on for some tokens. The model picks a few experts per token.

Attention

How the model looks back at earlier tokens to decide the next one.

KV cache

The notes a model keeps for every token it has read, so it doesn't redo work. It grows with the conversation.

Summary state

A fixed-size running summary that some layers keep instead of a note per token. It doesn't grow.

03Problem one: 896 experts that stay balancedStable LatentMoE

The idea. A mixture-of-experts model splits its parameters into groups and lets a router pick a few per token. More experts with fewer active per token means more total knowledge for the same work per token. K3 pushes this hard: 16 of 896 is under 2%.

Why it gets unstable. The video has a chapter on exactly this. The general problem in the field: when the router can pick from hundreds of experts, it tends to favour a few. Those get overloaded while others barely train, and the whole run can wobble. Labs fight this with balancing rules that push the router to spread tokens around. Moonshot calls its approach Stable LatentMoE and says it gives about 2.5 times the scaling efficiency of its previous model, K2. That figure is Moonshot's own.

What it costs at serving time. Less math per token, but the memory bill does not shrink, because every expert has to be loaded somewhere. This is why the rest of the session is about memory.

04Problem two: a million tokens of contextNotes vs summaries

A standard look-back layer keeps a note for every token it has read. On Baseten's whiteboard, K3's look-back layers need 13.5 KiB per token in total. That sounds small until you multiply: a full million-token conversation needs about 13 GiB of notes, for one person.

The summary layers work differently. Each conversation gets one fixed-size state, 27.7 MiB across all of K3's summary layers, whether the conversation is ten tokens or a million. Moonshot says its two architectural changes, Kimi Delta Attention and Attention Residuals, improve how information flows across sequence length and model depth. Baseten's session pairs Attention Residuals with the million-token context.

Exhibit 3. Memory per conversation: notes grow, the summary doesn't
Memory for one conversation as it gets longer (log scale). The look-back notes grow with every token. The summary state is flat. They cross at about 2,100 tokens: past that, the notes cost more than the summary for every conversation.
My math from the whiteboard: 27.7 MiB ÷ 13.5 KiB ≈ 2,101 tokens. 1,000,000 tokens × 13.5 KiB ≈ 12.9 GiB. Notes are summed across K3's 24 look-back layers and the summary across its 69 summary layers, as drawn on the board.
05The family tree of attentionFrom the whiteboard

The longest stretch of the video is Ali drawing how attention evolved. Each step fixed one problem and created the next. This is the shortest version I can give:

Exhibit 4. Six steps from "compare everything" to Kimi Delta Attention
Read left to right. Each box says what the step changed and what it cost.
Lineage: softmax attention (2017), linear attention (2020), the delta rule as used in DeltaNet, Gated DeltaNet (2024), and Kimi Delta Attention from Moonshot's Kimi Linear work (2025). The chapter titles in the video follow this order.

Why linear attention didn't win earlier. Two reasons come up in the field, and the video has chapters on both. A fixed-size summary can't hold everything, so exact recall suffers. And the update rule is sequential, which made it slow on GPUs built for big parallel matrix math. Newer methods rewrite the delta update into chunks that GPU tensor cores can run in parallel, and hybrids keep a few full look-back layers for exact recall. K3 does both.

06Fitting 2.8 trillion parameters on one machineThe memory budget

The most useful drawing in the session is a single GPU's memory budget. It decides how many people the model can serve.

Exhibit 5. One B300 GPU, 288 GB, as drawn on the whiteboard
Top: where the GPU's memory goes. Bottom: the 50 GiB set aside for conversation memory, and how many tokens or conversations it holds.
Redrawn from the whiteboard at about 56:00. The board's numbers sum to 288 and mix GB and GiB, as written. That the model is spread over eight GPUs is my reading of the 47:00 drawing; 2.8T parameters at about 4.25 bits is roughly 1.5 TB, or about 186 GB per GPU across eight, close to the 183 drawn.

Two ways to run out of room. The notes budget holds about 2.3 million tokens in total, across everyone. The summary budget holds about 527 conversations at once, however short. A service can hit either wall first: many short chats fill the summary slots; a few very long ones fill the notes. Capacity planning, pricing and rate limits all need both numbers.

07Splitting the model across eight GPUsTensor vs expert parallelism

A model this size doesn't fit on one chip, so it is split. There are two ways, and Bryce drew both.

Exhibit 6. Slice every layer, or hand out whole experts
Left: tensor parallelism gives every GPU one eighth of every layer, so all eight must talk after each layer. Right: expert parallelism gives each GPU whole experts, about 112 of 896 each, and sends each token to the GPUs that hold its experts.
In practice: vLLM's early K3 setup paired expert parallelism with data parallelism across 16 GPUs (DP16 + EP16). The trade: tensor parallelism means constant chatter between chips; expert parallelism means uneven traffic when popular experts sit on the same GPU.
08Two kinds of memory, one schedulerCaching and checkpoints

Serving systems save money by reusing work. If a thousand requests start with the same long instructions, the model should read them once and reuse the result. With per-token notes that is easy: keep the notes for the shared start and point new requests at them.

Summary layers make it harder. The summary is one blended state, not a list of notes, so you can't cut it at an arbitrary token. The fix is to save checkpoints of the summary at regular points (the video's chapter on KDA state checkpointing). A new request can then resume from the last checkpoint before the shared text ends. vLLM had to rebuild parts of its cache manager to do this, including partial reuse with copy-on-write.

Exhibit 7. Reusing a shared prompt when part of the memory is a summary
Two requests share a long opening. Notes can be reused token by token. The summary can only be reused from a saved checkpoint, so anything after the last checkpoint is recomputed.
09Reading, writing and guessing aheadDisaggregation and speculation

Every answer has two phases. Reading the prompt happens all at once and is limited by how fast the chip does math. Writing the reply happens one token at a time and is limited by how fast the chip can fetch weights and memory. Because the two phases stress different parts of the chip, large deployments now run them on separate GPUs. This is called disaggregation. The reading GPUs hand the conversation memory to the writing GPUs.

On the writing side, speculative decoding cuts the number of slow steps. A small, fast drafter guesses several tokens ahead, and the big model checks them all in one step, keeping the ones it agrees with. The session covers two recent drafters, DFlash and DSpark. DFlash, for example, drafts a whole block of tokens in one pass.

Exhibit 8. Separate the phases, then guess ahead
Top: reading and writing on different GPUs, with memory handed between them. Bottom: a drafter proposes four tokens, and the big model accepts three and fixes one in a single step.
10What it means if you build on modelsFor PMs
  • 01
    Capacity has two limits. Count tokens in flight and conversations in flight. Rate limits and load tests need both.
  • 02
    Long context is a pricing decision. One full million-token session uses over a third of a GPU's notes budget on the whiteboard's numbers. Price or limit long sessions separately.
  • 03
    Test exact recall by length. Summary layers can blur exact details over long distances. Check IDs, numbers and quotes at 8K, 128K, 512K and 1M tokens as separate slices, not one average.
  • 04
    Measure cost per finished task. Agents resend long shared instructions. With summary layers, cache reuse depends on checkpoints, so report the cache hit rate alongside cost.
  • 05
    The same weights can behave differently by provider. Compression formats, kernels and cache settings vary. Run your own tests on each provider's endpoint before choosing.
11Check yourselfAnswers fold out
Q1K3 uses 16 of 896 experts per token. Why doesn't that cut memory by the same ratio?
Because every expert must stay loaded; the next token may route to different ones. Experts cut the math per token, not the memory.
Q2Past roughly how many tokens does a conversation's notes cost more than its summary state?
About 2,100 tokens: 27.7 MiB ÷ 13.5 KiB per token.
Q3A service runs out of room with only 400,000 tokens in flight. What hit the limit?
Probably the conversation count: about 527 summary states per GPU on the whiteboard, regardless of length. Lots of short chats fill it first.
Q4Why is reusing a shared prompt harder with summary layers?
A summary is one blended state, so it can only be reused from a saved checkpoint, not cut at any token like a list of notes.
Q5What's the trade between tensor and expert parallelism?
Tensor: every GPU talks after every layer. Expert: less chatter, but uneven load when popular experts share a GPU.
Q6Why run reading and writing on different GPUs?
Reading is limited by math speed, writing by memory speed. Separating them lets each set of GPUs do what it is best at.
